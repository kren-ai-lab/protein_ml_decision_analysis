# Preprocessing and Cleaning

## Overview

This directory contains the final data-quality and formatting stages that prepare a merged binary-classification dataset for downstream computational pipelines.

The notebooks must be executed in the following order:

1. `preprocessing_data.ipynb`
2. `creating_raw_data.ipynb`

The first notebook applies sequence-level quality filters and records the filtering statistics. The second notebook selects the pipeline-facing columns and assigns deterministic sequential identifiers based on the retained row order.

Despite its name, `creating_raw_data.ipynb` does not recreate the original raw source files. It creates the compact, pipeline-ready `sequences.csv` input used by later workflow stages.

## Files and execution order

| Order | File | Purpose |
| ---: | --- | --- |
| 1 | `preprocessing_data.ipynb` | Filters merged consensus and unresolved sequences using canonical-residue and sequence-length criteria. |
| 2 | `creating_raw_data.ipynb` | Extracts `sequence` and `label`, generates `seq_<number>` identifiers, and exports the downstream pipeline input. |

The second notebook depends on an output generated by the first notebook and must not be executed first.

## Position in the data workflow

The directory is designed for use after source parsing and cross-source merging:

1. Process each source independently.
2. Merge source annotations and identify consensus or conflicting sequences.
3. Run `preprocessing_data.ipynb` to apply sequence quality controls.
4. Run `creating_raw_data.ipynb` to create the minimal pipeline input.
5. Run the downstream representation, partitioning, and modeling workflows.

This stage does not resolve annotation conflicts, recalculate consensus labels, or preserve every provenance column in the final pipeline input. Those responsibilities belong to earlier data-processing stages and their archived outputs.

## Stage 1: `preprocessing_data.ipynb`

### Purpose

This notebook applies the same sequence-quality criteria to:

- records with a final consensus label; and
- records previously separated because of annotation inconsistencies.

Keeping both groups in the quality-control stage makes it possible to distinguish annotation disagreement from invalid sequence content or unsupported sequence length.

### Configuration

The notebook defines the processed-data root as:

```python
path_to_export = "../../processed_dataset"
```

It reads:

```text
../../processed_dataset/merged_data/processed_dataset.csv
../../processed_dataset/merged_data/sequences_with_erros.csv
```

and writes to:

```text
../../processed_dataset/processed_data/
```

### Required inputs

#### `merged_data/processed_dataset.csv`

The notebook uses at least these columns:

| Column | Requirement |
| --- | --- |
| `sequence` | Protein sequence represented as a string. |
| `label` | Final binary label encoded as `0` or `1`. |
| `length` | Sequence length generated during the upstream merge stage. |

Other upstream columns, including source-specific annotations and consensus statistics, are retained in the filtered output.

#### `merged_data/sequences_with_erros.csv`

This file must contain a `sequence` column. A `length` column is computed by this notebook before filtering. Other upstream columns are retained.

### Quality-control procedure

#### 1. Sequence length completion

The notebook calculates the length of every sequence in the unresolved-record dataset:

```python
df_sequences_with_errors["length"] = (
    df_sequences_with_errors["sequence"].str.len()
)
```

The consensus dataset is expected to contain its `length` column already.

#### 2. Canonical-residue validation

`UtilsFunctions.checking_canonical_residues` is applied to the `sequence` column of both datasets. The result is stored in the boolean column `is_canon`.

The accepted vocabulary comes from `CANONICAL_RESIDUES` in the project constants. In the captured notebook environment, it corresponds to the 20 standard amino-acid symbols:

```text
A, C, D, E, F, G, H, I, K, L, M, N, P, Q, R, S, T, V, W, Y
```

Sequences containing unsupported characters do not pass this filter.

#### 3. Length validation

The notebook imports the project-wide length constants and then explicitly overrides the minimum length:

```python
MIN_LENGTH_SEQUENCE = 70
```

The effective accepted interval is inclusive:

```python
sequence_length.between(70, MAX_LENGTH_SEQUENCE)
```

The result is stored in `is_in_length`. `MAX_LENGTH_SEQUENCE` remains the value defined by the installed `building_models` package; it was `1024` in the notebook's recorded execution environment.

Because the minimum is overridden locally, changing the imported `MIN_LENGTH_SEQUENCE` constant alone will not change this notebook's effective lower bound.

#### 4. Combined filter

A record is retained only when both conditions are true:

```text
is_canon AND is_in_length
```

The filter is applied independently to consensus records and unresolved records.

### Outputs

The notebook creates `processed_data` when needed and writes:

```text
../../processed_dataset/processed_data/
├── metadata_process.json
├── processed_dataset.csv
└── sequences_with_errors.csv
```

Notice that the output uses the corrected spelling `sequences_with_errors.csv`, while the upstream input is named `sequences_with_erros.csv`.

#### `processed_data/processed_dataset.csv`

Contains consensus-labeled sequences that pass both quality filters. It retains the upstream columns and adds:

| Column | Description |
| --- | --- |
| `is_canon` | Whether the sequence contains only accepted canonical residues. |
| `is_in_length` | Whether the sequence length is within the inclusive configured interval. |

All records in this output should have both flags set to `True`.

#### `processed_data/sequences_with_errors.csv`

Contains unresolved annotation records that nevertheless pass the sequence-quality filters. It retains the upstream annotation information and adds `length`, `is_canon`, and `is_in_length`.

These records remain separate because preprocessing does not resolve their annotation conflicts.

#### `processed_data/metadata_process.json`

The metadata records counts before and after filtering:

| Section | Recorded information |
| --- | --- |
| `total_data` | Initial counts for consensus and unresolved records. |
| `canonical_sequences` | Accepted residue vocabulary and canonical/noncanonical counts for both groups. |
| `length_evaluation` | Effective minimum and maximum lengths and pass/fail counts for both groups. |
| `final_evaluation` | Final consensus count, positive and negative class counts, and the retained unresolved count. |

The metadata reports each filter independently. Consequently, the number failing the final combined filter cannot always be obtained by adding the individual failure counts because one sequence may fail both criteria.

## Stage 2: `creating_raw_data.ipynb`

### Purpose

This notebook converts the filtered consensus dataset into the minimal schema required by downstream pipelines.

It does not consume `processed_data/sequences_with_errors.csv`; unresolved annotations remain excluded from model-ready data.

### Configuration

The notebook defines:

```python
path_data = "../../processed_dataset"
path_export = "../../pipelines/data"
```

It reads:

```text
../../processed_dataset/processed_data/processed_dataset.csv
```

and writes:

```text
../../pipelines/data/sequences.csv
```

Unlike the preprocessing notebook, it does not create the destination directory. Ensure that `../../pipelines/data` exists before execution.

### Formatting procedure

The notebook performs the following operations in order:

1. Loads the filtered consensus dataset.
2. Selects only `sequence` and `label`.
3. Assigns identifiers in the current row order.
4. Writes the resulting table without the pandas index.

Identifiers follow this format:

```text
seq_1
seq_2
seq_3
...
```

The identifier is positional. If input rows are added, removed, or reordered, identifiers may change even when the sequences themselves are unchanged.

### Output schema

`pipelines/data/sequences.csv` contains exactly these columns in the current implementation:

| Column | Description |
| --- | --- |
| `sequence` | Filtered canonical sequence. |
| `label` | Binary target label. |
| `id` | Sequential identifier generated as `seq_<one-based row number>`. |

Source-specific annotations, consensus counts, sequence lengths, and quality-control flags are intentionally omitted from this compact pipeline input. They remain available in `processed_data/processed_dataset.csv` for provenance and auditing.

## Validation

Run these checks from the notebook directory after both stages finish:

```python
import json
from pathlib import Path

import pandas as pd

processed_root = Path("../../processed_dataset/processed_data")
pipeline_file = Path("../../pipelines/data/sequences.csv")

processed = pd.read_csv(processed_root / "processed_dataset.csv")
unresolved = pd.read_csv(processed_root / "sequences_with_errors.csv")
metadata = json.loads((processed_root / "metadata_process.json").read_text())
sequences = pd.read_csv(pipeline_file)

# Stage 1 invariants
assert processed["sequence"].is_unique
assert processed["is_canon"].all()
assert processed["is_in_length"].all()
assert unresolved["is_canon"].all()
assert unresolved["is_in_length"].all()
assert set(processed["label"].unique()).issubset({0, 1})
assert len(processed) == metadata["final_evaluation"]["processed_sequences"]
assert len(unresolved) == metadata["final_evaluation"]["sequences_with_errors"]

# Stage 2 invariants
assert list(sequences.columns) == ["sequence", "label", "id"]
assert sequences["sequence"].is_unique
assert sequences["id"].is_unique
assert sequences["id"].tolist() == [
    f"seq_{index}" for index in range(1, len(sequences) + 1)
]
pd.testing.assert_frame_equal(
    sequences[["sequence", "label"]],
    processed[["sequence", "label"]],
    check_dtype=False,
)
```

The uniqueness assertions assume that the upstream merging stage produces one record per sequence. If duplicates are intentionally supported in a future workflow, update both the identifier policy and these checks.

## Operational considerations

- Run the notebooks in the documented order; the second stage depends on the first stage's output.
- The consensus input must already include `length`; only the unresolved dataset receives a newly computed length in the preprocessing notebook.
- The effective minimum sequence length is hard-coded to `70` after importing the shared constants.
- The effective maximum depends on the installed version of the `building_models` package.
- Both quality-control flags are retained in the processed outputs rather than removed after filtering.
- The pipeline export directory must already exist.
- Sequential IDs depend on input row order and are not stable sequence-derived identifiers.
- Existing CSV and JSON outputs are overwritten when the notebooks are rerun.
- Neither notebook exposes command-line arguments or performs explicit schema validation before processing.

## Reproducibility recommendations

- Preserve the merged inputs, filtered outputs, metadata, and pipeline-facing CSV for each release.
- Record the repository commit and the installed `building_models` version.
- Pin pandas and the Jupyter execution environment.
- Record the effective `MAX_LENGTH_SEQUENCE` value in each run.
- Keep row ordering stable when downstream artifacts refer to `seq_<number>` identifiers.
- Treat changes to the accepted residue vocabulary, length thresholds, filtering logic, or identifier policy as changes to the data-processing method.
